# Authentication and authorization

PamatiAI exposes server-enforced authentication and resource authorization. Accounts have institutional roles STUDENT, COUNSELOR or ADMIN. The migration renames the previous SYSTEM_ADMINISTRATOR role to ADMIN without discarding its memberships. Role codes submitted by a registrant are rejected.

Passwords use Argon2id, with rehash on login when parameters change. New passwords require 15–128 characters. Login failures use generic errors and persistent, hashed IP/account throttle buckets shared across workers. Public recovery requests return the same response for known and unknown accounts. Credentials, email link tokens and sensitive content are excluded from audit events.

Opaque access tokens last 15 minutes by default. Refresh tokens rotate once per use and have an absolute seven-day session lifetime. Only SHA-256 digests of bearer tokens are stored. Replaying a consumed refresh token revokes its whole session family. Logout, password reset/change, deactivation and role changes revoke applicable sessions immediately. Current account status, roles and permissions are read from the database on each protected request. User-row locking serializes credential changes and refresh; sessions are re-read with locking reads to avoid stale MySQL snapshots.

The browser uses a fixed-origin Next.js gateway: access and refresh tokens reside in HttpOnly, SameSite=Strict cookies, with Secure enabled in production. Tokens are never returned to browser JavaScript or placed in localStorage. Mutations require an exact Origin match. The backend accepts bearer credentials, not browser cookies. Account email links use URL fragments and the browser removes the fragment after loading. Sensitive responses use Cache-Control: no-store.

Students can read only their own conversations and safe numeric trend summaries, change their own consent, request human support, and submit their own export/erasure requests. Counselors require a current, non-revoked assignment, an active reviewer profile and the latest unwithdrawn student consent allowing reviewer access. Safety signals, human-review notes and referrals require counselor review permission. Checks derive ownership from the actual conversation/signal/referral record; arbitrary IDs cannot change ownership. Administrator account/configuration grants confer no student-content access. Role changes replace membership with one institutional role and revoke sessions.

AuditLog records login failures/successes, rate limiting, recovery/activation, session rotation/replay/logout, password changes, role/state/profile changes, assignments, configuration changes and sensitive reads/writes. Existing MySQL triggers prevent audit updates/deletes. Use separate migration and runtime database credentials; runtime credentials must not have schema/trigger privileges. Retain audit events according to institutional policy without adding messages, notes, passwords, tokens or connection strings.

See [AUTHENTICATION.md](AUTHENTICATION.md) for deployment and endpoint details. Implementation follows [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) and [single-use password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

Production deployment still requires HTTPS, explicitly configured hosts/origins, managed secrets, encrypted storage/backups and operational monitoring. The development Compose file uses reload and is not a production launch configuration. Staff MFA/institutional SSO is not implemented. Export/erasure and human-support requests are durable queues: this change does not claim to complete external fulfillment, notify emergency services, or purge object stores/backups. Maintain the existing consent and AI safety requirements before collecting participant data.

Student consent now has immutable disclosure/retention snapshots and timestamped receipt history. Server-side worker gates check permission before adapter invocation and before publication, cancel work on consent changes and reject optional payloads outside the saved input manifest. Student privacy inventories remain owner-only. Retention holds are finite and auditable; they do not confer content or processing permissions.
